# 通知公文

把明确的行政事项写成可办理、可复核的文稿。用户只要正文就直接给全文；要 Word 才制作文件，不为短通知强制走完整排版流程。

## 先选任务

| 请求 | 做法与按需资料 |
| --- | --- |
| 起草通知、请示、通报、函、通告/启事 | 从 [文种模板](references/notice-templates.md) 选择用途相符的一种；不把示例事实带进真实稿 |
| 润色、压缩、指定替换 | 保留原意、数字、责任与范围；指定替换之外逐字保留，交付完整改后稿 |
| 只审校 | 列“位置、问题、依据、建议”，区分错误、待核实与表达建议，不直接重写 |
| 仅排版、Word、正式版式 | 读取 [排版与引擎选择](references/format-spec.md)，用户模板优先，保留业务文字 |

## 写稿前确定事实

先用用户材料和上下文提取文种、发文主体、接收对象、事项、时间地点、办理动作/期限。只集中问会改变执行安排的缺口；用户要先出草稿时，缺项以【待确认：字段】入稿，稿外汇总。不强求每份通知都有报名截止或联系电话。

- “下周五”等先按会话日期与用户时区换算，交代采用的绝对日期；星期与日期冲突时询问，不擅自二选一。
- 联系方式、金额、批准状态、政策文号、处罚依据只取已给或核实来源。没有批示不能写“经研究决定”。联系人可省略；确需联系方式再留占位。
- 请示一文一事；一般通知可围绕同一主题分条部署，不能把“一文一事”机械套到所有文种。
- 引用政策时记原文标题、发文机关、日期和链接；未查到原文时保留待核实状态，不把网络范文当用户事实。

## 成稿与交付

先写对象要做的动作，再补必要背景和执行要求；条款层次用“一、（一）1.（1）”。收文/发文身份与行文关系一致，附件题名与实际文件一致。不得添加未经提供的问责、默认同意或放弃权利条款。

可把日期元数据放入 JSON，运行 [日期检查脚本](scripts/check.py)：

```text
python "<本技能目录>/scripts/check.py" "<输入.json>"
```

输入见 [检查接口与样例](references/validation.md)。脚本只检查显式输入的日期、星期、先后关系和缺项，不代替全文审校。

交付前对照原始材料核数字、日期、对象、办理方式、落款。制作 Word 后读回文字、检查页边距与字体；有可用渲染器时逐页查看断行、表格、页码和落款。工具存在、文件可读、渲染通过是不同证据；未渲染要说明。

最终按请求给正文或实际文件链接，另列必要待确认项；用户要求“只给正文”时不附制作过程。正式红头、签发人、印章和文号沿用用户模板与发文制度，不能凭空补齐或声称已正式签发。
